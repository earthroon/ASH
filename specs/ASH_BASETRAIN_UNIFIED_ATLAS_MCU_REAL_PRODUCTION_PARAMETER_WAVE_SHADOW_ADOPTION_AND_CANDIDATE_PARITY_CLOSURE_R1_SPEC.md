# 1. Purpose

P0 closed physical qualification evidence truth.

P1 closed immutable qualification publication and one-current-bundle adoption.

P2 leaves bounded qualification fixtures and binds the currently adopted MCU authority to **actual production Muon local Waves** produced inside the live optimizer callsite.

The core question is:

> Given the exact live production Wave, does a non-authoritative replay through the exact selected R8/R8A execution route reproduce the authoritative production candidate without gaining any commit authority?

---

# 2. Source-derived physical correction

The current parent source already allows the production Muon path itself to execute through:

`R6 -> R8 -> R8A -> existing TensorCubeLocalMuonBatchExecutor`.

There is no separately preserved pre-MCU legacy executor that can honestly be called a second production SSOT.

Therefore P2 R1 defines:

- **canonical execution** = the first authoritative live production execution already performed by the current ProductionMuonRuntime;
- **shadow execution** = a second non-authoritative replay of the same real Wave through the exact same selected homogeneous expert or exact same R8A indexed expert plan;
- **commit authority** = canonical production path only.

P2 must not fabricate a legacy-vs-MCU comparison authority that the source tree no longer contains.

---

# 3. MirrorVerified transfer correction

The current streaming parent requires `MuonDeviceCandidateRuntimeMode::MirrorVerified` and host-observed candidate materialization for existing production evidence/commit compatibility.

Therefore P2 R1 does **not** claim zero additional H2D/D2H for the shadow replay.

Instead P2 records exactly:

- shadow descriptor upload bytes;
- shadow weight upload bytes;
- shadow momentum upload bytes;
- shadow candidate-weight readback bytes;
- shadow candidate-momentum readback bytes;
- shadow update readback bytes;
- shadow status readback bytes.

These counters are evidence, not hidden overhead.

Zero-transfer GPU-resident shadow comparison is a later optimization revision and is not a P2 R1 correctness prerequisite.

---

```text
same real production Wave pre-state
        |

        |       |
        |       +--> production candidate

production candidate

```

`Live Input Authority != Shadow Replay Authority != Commit Authority`.

Live input authority remains the existing ProductionMuonRuntime callsite.

Shadow authority is the P2 observer bound to the P1 current immutable qualification bundle.

Commit authority remains the existing canonical optimizer path.

# 21. Production priority

Canonical production execution always happens first.

P2 shadow replay happens only after canonical execution returned successfully.

Therefore a P2 observer cannot prevent the canonical candidate from being computed merely because the optional shadow path was unavailable.

# 22. Canonical commit preservation

Shadow candidate buffers/vectors are never passed to the production commit coordinator.

There is no:

`commit_shadow()`.

There is no:

`use_shadow_candidate()`.

There is no canonical-failure fallback to shadow output.

---

# 23. Exact live pre-state

For the streaming local Wave, P2 shadow replay consumes the exact host-side source and momentum slabs already prepared for the canonical Wave before commit mutation.

When slab reuse is active:

- `source_wave_slab[..wave_elements]`;
- `momentum_wave_slab[..wave_elements]`.

Otherwise:

- the exact current local weight vector;
- the exact current local momentum vector.

The canonical executor does not mutate these host input slices.

---

# 24. Exact descriptors

P2 reuses the exact `execution_descriptors` selected for the canonical physical Wave.

If R6 active execution descriptors were used by production, the same descriptor list is passed to the shadow replay.

No convenient repacked fixture geometry substitutes for the live descriptors.

---

# 25. Exact R8 expert assignment

For homogeneous Active R8:

- use the exact `r8_execution_expert` selected by the canonical path.

For R8A:

- use the exact `TensorCubeLocalMuonExpertBucketExecutionPlanR8A` already materialized for the canonical path;
- preserve exact packed descriptor indices;
- preserve exact E0/E1/E2 bucket counts.

No rerouting occurs between canonical and shadow execution.

---

# 26. R8A expert-map reconstruction

The existing R8A contract packs descriptor indices in stable expert order:

`E0 -> E1 -> E2`.

P2 reconstructs per-canonical-job expert ownership from:

- packed descriptor index position;
- E0 count;
- E1 count;
- E2 count.

Every job must receive exactly one expert owner.

---

# 27. Shadow executor

P2 creates no new GPU Device, Queue or shader authority.

It reuses the existing `TensorCubeLocalMuonBatchExecutor`.

Homogeneous replay:

`execute_qualification_with_expert_r7`.

Indexed replay:

`execute_qualification_with_expert_buckets_r8a`.

These APIs are replay mechanisms only; they do not acquire commit authority.

---

# 28. Why qualification execution API is reused

The qualification execution functions provide an isolated non-resident output surface while using the same already-built R7/R8A physical kernels.

This avoids a second resident-state-graph write for the same candidate generation, which the B04A state machine correctly rejects as duplicate partition mutation.

---

# 29. No duplicate resident partition write

P2 must not call the resident production executor a second time against the same B04A partition identity.

That would collide with:

`FAIL_B04_DUPLICATE_PARTITION_WRITE`.

The shadow replay is therefore physically isolated from the resident commit graph.

# 47. Promotion states

`OFF`:

P2 not enabled.

`SHADOW_ONLY`:

P2 enabled but physical promotion evidence is incomplete.

`FAILED`:

an admitted shadow Wave diverged or shadow execution failed.

`PROMOTED`:

mandatory real-Wave parity evidence closed.

---

# 48. Minimum promotion cardinality

`PROMOTED` requires:

- admitted real Wave count > 0;
- nonzero real Wave count > 0;
- multi-job real Wave count > 0;
- passed count == admitted count.

A zero-size or one-job-only demonstration is insufficient.

---

# 49. Divergence gates

For `PROMOTED`:

- nonfinite divergence count = 0;
- status divergence count = 0.

The exact bucket plan is consumed, but lifecycle authority stays canonical.

# 76. P2 PASS semantics

P2 PASS means:

> The P1 current immutable MCU authority was pinned into a real ProductionMuonRuntime campaign. One or more nonzero multi-job local Muon Waves from the actual production execution callsite were executed authoritatively and then replayed through the exact live selected R8 homogeneous expert or R8A indexed expert plan using the same live descriptors and pre-commit source/momentum inputs. The shadow result did not acquire commit authority. Candidate weight, candidate momentum, orthogonal update and tile status satisfied the exact expert-owned comparison contract for every admitted Wave. Shadow optimizer commit, generation advance, checkpoint commit and Physical N2 writes remained zero. Actual replay transfer overhead was measured rather than hidden.
